# Repository Guidelines

## Project Structure & Module Organization
`UserCode/` contains the application-owned C++ logic and is the main place for feature work. `Core/`, `Drivers/`, and `Middlewares/` are STM32CubeMX-generated outputs; change the `.ioc` file and regenerate instead of hand-editing those folders. `Modules/` holds `cpkg`-managed package repositories such as `BasicComponents`, `ChassisController`, `MotorDrivers`, and `VelocityProfile`. Toolchain files live in `cmake/`, and `cmake/wtr_modules.cmake` is generated by `cpkg sync`. Local build artifacts go under `build/`.

## Build, Test, and Development Commands
Use the presets already checked into the repo:

- `cmake --preset Debug`: configure a Debug build with Ninja and `gcc-arm-none-eabi`.
- `cmake --build --preset Debug`: build the firmware into `build/Debug/`.
- `cmake --preset Release`
- `cmake --build --preset Release`: produce the optimized firmware build.
- `cpkg sync`: refresh `Modules/` and regenerate `cmake/wtr_modules.cmake` after dependency changes.
- `stm32tool generate`: regenerate CubeMX-managed sources after editing `26-V3.0-R1-MCU1.ioc`.

## Coding Style & Naming Conventions
Formatting follows `.clang-format`: 4-space indentation, no tabs, Allman braces, C++17, and a 100-column limit. Prefer `clang-format -i <file>` on touched C/C++ files before submitting. Match the existing naming patterns: `PascalCase` for classes and structs, `snake_case` for files and most functions, and uppercase macro names. Keep includes stable; the formatter does not sort them.

## Testing Guidelines
There is no repository-wide automated test suite or `ctest` setup yet. At minimum, validate changes by rebuilding the affected preset and checking for link errors. If you add tests or simulations, keep them near the owning module, follow names like `module_name_test.cpp`, and document the run command in that module.

## Commit & Pull Request Guidelines
Recent history uses short `feat` and `fix` prefixes, often with Chinese summaries. Follow the same structure with a concise subject, for example `feat: add chassis calibration guard` or `fix(controller): handle UART timeout`. Pull requests should state what changed, which folders were touched, how it was validated, and whether `.ioc`, generated code, or `Modules/` dependencies changed.

## Generated Code & Dependency Notes
Do not edit `cmake/wtr_modules.cmake` manually. When adding dependencies, update the manifest through `cpkg` rather than editing generated integration files by hand.

## Agent-Specific Instructions
If there are important repository changes, update this `AGENTS.md` promptly so the guide stays current for future contributors.
